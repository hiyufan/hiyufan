# AI 智能拓展功能说明

题目给出的 4 项全部实现，另加一项"智能派单推荐"。全部功能默认**本地离线运行**，不依赖外网和第三方库。在 `backend/.env` 中填写 `LLM_API_KEY` 后，故障诊断和单张工单摘要会优先调用大模型；接口调用失败时自动回到本地方案，前端会显示当前用的是哪种引擎。

|---|---|---|---|---|
| ① 故障智能诊断 | 规则推理 + 案例推理（CBR）+ 同义词扩展，noisy-OR 合成 | `POST /api/ai/diagnose` | 报修页右侧"故障初判"、派单弹窗、完工弹窗预选类别 | `services/ai/diagnosis.py` |

## ① 故障智能诊断

**功能**：员工输入故障描述时，实时给出 1~3 个可能的故障类别。每个类别附带可能原因、处理建议、置信度和依据（命中的关键词、相似的历史工单），并提示安全风险。设备科派单时用同一结果推荐维修工。

**为什么不只用关键词规则**：规则只认识写进知识库的说法。员工说"加热不上来"、"抬不起来"、"屏幕不亮"，规则一个都匹配不上。而这类故障以前很可能修过，历史工单里有答案。

**算法**：两路证据各自估计"属于类别 c"的置信度，再合成。

1. **规则证据**（专家经验）
   `fault_knowledge` 表每条规则有一组关键词。命中关键词的总字数为 s，则规则置信度
   `r(c) = s / (s + 4)`。命中约 4 个字时为 0.5，之后增长放缓。同一类别取最有把握的那条规则。

2. **案例证据**（历史数据），参考 Aamodt & Plaza (1994) 提出的 CBR 循环 retrieve → reuse → revise → retain：
   - **retrieve**：用 BM25（见 ②）从已归档工单中取最相似的 K=5 个案例，匹配度低于 0.12 的不要；
   - **reuse**：每个案例带有维修工完工时确认的故障类别，按相似度加权投票
     `vote(c) = Σ sim(属于 c 的案例) / Σ sim(全部案例)`；
     再乘以可信度 `min(1, 最高相似度 / 0.5)`：最像的案例也不太像时，整体证据要打折。
     `case(c) = min(0.9, vote(c) × 可信度)`；
   - **revise / retain**：维修工完工时必须确认实际故障类别（系统用初判预选，维修工按现场修改），归档后自动成为新案例。系统用得越久，案例越多，诊断越准。

3. **合成**：noisy-OR，`P(c) = 1 − (1 − r(c)) × (1 − case(c))`。
   假设两路证据独立：任一路有把握，结论就有把握；两路都支持时置信度更高。结果不会低于任何一路单独的置信度。

4. **同义词扩展**（查询扩展）：`text.py` 中维护车间口语到标准术语的对照表，如"往一边偏 → 跑偏"、"抬不起来 → 无法起升"。命中口语说法时，把标准术语追加到文本后再做匹配，原文不删除。

5. **安全风险**：描述中出现"冒烟、焦糊、漏电、光栅、急停"等词时判为高风险，提示断电挂牌，并自动把紧急程度调为"紧急"。

**评测**（`python scripts/eval_diagnosis.py`）：24 条手写的车间口语描述，刻意不用知识库里的原词。

| 方案 | 覆盖率 | Top-1 准确率 | Top-3 准确率 |
|---|---:|---:|---:|
| A 仅规则 | 50% | 46% | 50% |
| B 规则 + 案例推理 | 88% | 88% | 88% |
| C 规则 + 案例推理 + 同义词扩展 | 96% | 96% | 96% |

> 局限：测试集和同义词表是同一批人写的，结果偏乐观。要得到可信的数字，应收集员工真实写的报修描述作为测试集。另外，案例库只有 29 条带标签的历史工单，类别多的故障更容易被投票选中。

## ② 维修知识库检索

**功能**：已归档工单的"故障现象 + 故障类别 + 处理方法"自动进入知识库。输入一个现象，按相似程度列出以前的修法，并高亮命中的字词。

**切词**：中文按字二元组切分（"主轴异响" → 主轴 / 轴异 / 异响），英文和数字按整词保留。这是中文检索中不需要分词词典的常用做法，考场离线也能运行。"轴异"这类无意义片段会在 IDF 中被自动降权。

**排序**：Okapi BM25（Robertson & Zaragoza, 2009），Lucene / Elasticsearch 的默认相关性算法：

```
score(q, d) = Σ_{t∈q} idf(t) · tf(t,d)·(k1+1) / (tf(t,d) + k1·(1 − b + b·|d|/avgdl))
idf(t)      = ln(1 + (N − n(t) + 0.5) / (n(t) + 0.5))        k1 = 1.2，b = 0.75
```

相比最初版本的 TF-IDF 余弦相似度，BM25 多了两点：
- **词频饱和**：同一个词出现很多次，得分增长放缓，不会被重复描述"刷分"；
- **长度归一**：长文档天然更容易命中，按文档长度与平均长度之比打折。

为了在界面显示"匹配度"，把得分除以理论上限 `Σ idf(t) · (k1+1)`，得到 0~1 之间的值。建索引时故障现象重复一次，相当于给"现象"字段加权（BM25F 的简化做法），因为用户检索时输入的是现象。

索引缓存在内存中，归档工单数量或最新归档时间变化时自动重建。单元测试 `tests/test_algorithms.py` 验证了相关性排序、词频饱和、长度归一三条性质。

## ③ 工单智能摘要

**功能**：把一张工单压缩成一句话加几个结构化字段（设备、位置、故障类型、风险等级、现象、处理、处理时长），用于派单页和看板快速浏览。

**实现**：故障类型优先取维修工已确认的类别，没有时用 ① 的诊断结果；风险等级复用 ① 的风险词规则；现象和处理取首句并截断。批量生成（列表、看板）始终走本地规则，避免逐条请求大模型拖慢页面；查看单张工单时如果配置了大模型，摘要文字由大模型生成，结构化字段仍由规则保证准确。

## ④ 超期工单预警

**功能**：超过 48 小时未派单或未完工的工单，在看板顶部用警示带集中列出。设备科可以一键处理：未派单的自动派给推荐得分最高的维修工，未完工的向维修工发出催办（记入流转日志）。

**实现**：
- 随服务启动的后台任务（`asyncio`）每 5 分钟扫描一次。数据库操作放在线程池中执行，不阻塞接口；任何异常只写日志，不会让服务崩溃；
- 扫描是幂等的：已有未处理预警的工单只更新超时小时数，不重复创建。工单状态变化后，预警自动解除；
- 人工处理过的预警在 48 小时内不再重复提醒。否则"催办"后工单仍超期，下一次扫描又会生成新预警，催办等于没生效。这个问题在开发中由测试发现，已修复并有用例覆盖；
- 查询预警和看板指标前也执行一次扫描，数据库刚初始化时不必等定时任务。

阈值和扫描间隔可在 `.env` 中配置（`ALERT_THRESHOLD_HOURS`、`ALERT_SCAN_INTERVAL_SECONDS`）。

## ⑤ 智能派单推荐

**功能**：派单时列出所有在岗维修工的推荐得分和理由，例如"擅长液压故障 · 在手 1 单 · 修过同类 3 次 · 满意度 4.7"，得分最高的默认选中。

**算法**：多准则加权打分（简单加权法 SAW），各项先归一到 0~1：

| 准则 | 权重 | 归一化方式 |
|---|---:|---|
| 擅长方向包含本次故障类别 | 40% | 是 1，否 0 |
| 空闲程度 | 30% | 1 / (1 + 在手单数) |
| 同类故障经验 | 15% | n / (n + 2)，n 为已归档的同类工单数 |
| 历史满意度 | 15% | (平均分 − 1) / 4；还没有评价的按 0.6 计算，避免新人永远排不上 |

权重体现设备科的派单习惯：先看会不会修，再看忙不忙，最后参考经验和口碑。权重集中定义在 `RECOMMEND_WEIGHTS`，可按企业实际调整。

## 大模型接口方案（可选）

- 协议：OpenAI Chat Completions 兼容接口（DeepSeek、通义千问、Kimi 等均支持），只用 Python 标准库 `urllib` 调用，不增加依赖；
- 配置：`.env` 中的 `LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL`；
- 约束：提示词要求只输出 JSON，类别必须来自 6 个固定类别，不在列表中的结果丢弃；
- 降级：超时（默认 15 秒）、网络错误、返回格式不对时返回空结果，自动使用本地方案。
