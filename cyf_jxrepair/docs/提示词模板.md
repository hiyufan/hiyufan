# 结构化提示词模板

4 类模板，每类都包含 **技术栈约束、功能描述、输出格式、代码注释规范** 四个要素。`{花括号}` 内是每次使用时替换的内容。

> 使用建议：一次只让 AI 生成一个模块。生成后先跑通、再审查，不要一次生成整个系统。审查时重点检查第 5 节列出的易错点。

---

## 1. 数据库设计

```text
【角色】你是 MySQL 数据库设计工程师。

【技术栈约束】
- MySQL 8.0，InnoDB，字符集 utf8mb4，排序规则 utf8mb4_0900_ai_ci
- 数据库名 cyf_jxrepair；表名小写下划线；每张表必须有自增主键 id
- 时间字段用 DATETIME，created_at 默认 CURRENT_TIMESTAMP，updated_at 加 ON UPDATE CURRENT_TIMESTAMP
- 固定取值的字段（角色、状态）使用 ENUM，存英文编码
- 必须建立外键约束；禁止在业务表中冗余存储可通过外键查到的名称类字段

【功能描述】
为"设备报修工单系统"设计 {表名列表，如：sys_user, device, repair_order, order_log, repair_evaluation}：
- {逐表写清业务含义与关键字段，如：repair_order 需要工单编号（CYF+日期+3 位流水）、状态（待派单/待接单/维修中/待验收/已归档/已驳回）、故障描述、照片路径、处理结果}
- 表之间的关系：{如：工单通过 device_id 关联设备，通过 reporter_id / repairer_id 关联用户}
- 需要的索引：{如：按状态 + 时间查询列表}

【输出格式】
1. 一个可直接执行的 .sql 文件：DROP DATABASE IF EXISTS → CREATE DATABASE → 按外键依赖顺序建表
2. 之后单独输出一张 Markdown 表，列出每张表的字段、类型、约束、说明
3. 最后用 3~5 句话说明表之间的关系

【代码注释规范】
- 每张表、每个字段都写 COMMENT（中文）
- 每张表前用 -- 注释块写明表的用途；ENUM 字段在 COMMENT 中列出每个值的中文含义
```

## 2. 后端接口

```text
【角色】你是 Python 后端工程师。

【技术栈约束】
- Python 3.10+、FastAPI、SQLAlchemy 2.0（Mapped 风格）、PyMySQL、Pydantic v2
- 分层：routers（路由与参数校验）→ services（业务逻辑）→ models（ORM），路由函数里不写 SQL
- 统一响应 {"code": 200, "message": "", "data": ...}；错误通过抛出业务异常由全局异常处理器转换
- 所有查询使用 ORM 参数绑定，禁止字符串拼接 SQL；密码只存哈希

【功能描述】
实现接口：{方法 + 路径 + 用途，如 POST /api/orders/{id}/dispatch 派单}
- 调用者角色：{如：仅设备科管理员}
- 前置状态与校验：{如：工单必须为"待派单"；维修工必须在岗；已归档工单不可变更}
- 成功后的效果：{如：状态改为"待接单"，记录派单人与时间，写一条流转日志}
- 失败情况与返回码：{如：无权限 403，状态不对 409，工单不存在 404}

【输出格式】
1. 只输出需要新增或修改的文件，每个文件以"文件路径"开头，给出完整代码
2. 列出新增接口的请求示例与返回示例（JSON）
3. 给出 2~3 个 pytest 用例，覆盖成功与越权两种情况

【代码注释规范】
- 模块顶部用 docstring 说明用途；公共函数写 docstring，说明参数与返回值
- 业务规则（为什么这样判断）写在注释里，不解释显而易见的语法
- 路由使用 summary 参数写中文说明，便于 /docs 展示
```

## 3. 前端页面

```text
【角色】你是前端工程师。

【技术栈约束】
- 原生 HTML + CSS + JavaScript（ES Modules），不使用 Vue/React/jQuery，不使用任何外网 CDN
- 请求统一使用 js/core/http.js 的 api.get / api.post / api.upload；页面框架使用 js/core/layout.js 的 mountLayout
- 颜色只使用 css/base.css 中定义的变量；状态色遵循 GB 2893（黄警告、蓝指令、绿安全、红禁止）
- 所有来自接口的文字渲染前必须经过 esc() 转义；需兼容 Chrome / Edge 最近 3 年的版本

【功能描述】
页面：{文件名，如 dispatch.html 派单页}，使用角色：{如：设备科管理员}
- 页面要展示：{如：待派单工单列表，紧急、超期的排在前面}
- 交互：{如：点击"派单"弹出确认弹窗，选择维修工后提交；成功后提示并刷新列表}
- 调用接口：{如：GET /api/orders?status=PENDING、POST /api/orders/{id}/dispatch}
- 空数据、加载中、接口失败三种情况分别如何显示

【输出格式】
1. 先给出 HTML 骨架，再给出页面 JS，最后给出新增的 CSS（只给新增部分）
2. 每个文件以"文件路径"开头，给出完整代码

【代码注释规范】
- 每个 JS 文件顶部一行注释说明页面职责
- 每个函数上方用一行注释说明做什么；复杂交互写明原因
- 人工修改处使用注释标注：/* 人工优化-cyf：说明 */
```

## 4. BUG 排查

```text
【角色】你是有经验的全栈调试工程师，请先分析原因，再给修改方案。

【技术栈约束】
- 项目技术栈：FastAPI + SQLAlchemy 2.0 + MySQL 8.0 + 原生 JS；运行环境 {Windows 11 / Python 3.x / Chrome 版本}
- 只修改与问题直接相关的代码，不顺手重构；不得通过删除校验或关闭测试来"解决"问题

【功能描述】
- 现象：{发生了什么，期望是什么}
- 复现步骤：{1. 以 xx 账号登录 2. 点击 xx 3. ...}
- 报错信息：{完整的后端日志 / 浏览器控制台报错 / 接口返回 JSON}
- 相关代码：{粘贴相关文件片段，注明文件路径与行号}
- 已经尝试过：{做过哪些排查，结果如何}

【输出格式】
1. 原因分析：按可能性从高到低列出 1~3 个原因，每个说明依据
2. 验证方法：如何确认是哪一个原因（加日志 / 查数据库 / 断点）
3. 修改方案：给出修改前后的代码对比
4. 回归检查：修改后需要重新验证哪些功能

【代码注释规范】
- 修改处添加注释：# 人工修改-cyf：修复 xxx（原因：xxx）
- 注释写"为什么这样改"，不写"改了什么"（改了什么看 diff 即可）
```

## 5. 审查 AI 生成代码时的重点检查项

结合本项目开发过程，AI 生成的代码最容易在以下地方出错，生成后应逐项检查：

| 类型 | 检查什么 | 本项目中的对应位置 |
|---|---|---|
| 业务逻辑漏洞 | 状态流转是否校验了"谁、什么状态、是不是本人"；已归档能否被修改 | `services/workflow.py` |
| 数据越权 | 列表和详情是否按角色限定数据范围，而不只是隐藏前端按钮 | `order_service.scope_filter` |
| 安全隐患 | 密码是否明文或 md5；SQL 是否拼接字符串；上传是否只看扩展名 | `core/security.py`、`file_service.py` |
| 库与版本幻觉 | 调用的库是否真的装了；API 是否适用当前版本（如 Python 3.10 没有 `datetime.UTC`） | `requirements.txt` |
| 前后端约定不一致 | 前端处理 401 的方式是否误伤登录接口本身的 401 | `frontend/js/core/http.js` |
| 冗余重复 | 同一段校验或拼装在多处复制 | `order_service._transit` 统一流转模板 |
